CHAPTER 01

The system you will build

Understand the client/server boundary, tools, and the dataset.

PostgreSQL is a database server, not a file that VS Code opens directly. VS Code is a client: it sends SQL over a connection; the server parses, plans, and executes the query against durable tables. We will use a miniature online store with four related tables and the same example throughout.

Learning outcome: by the end, you can create the database, connect from VS Code, write grouped and joined queries, and interpret a query plan. PostgreSQL syntax is used throughout; example output is derived from the included small dataset, not a performance benchmark.

CHAPTER 02

Install and initialize PostgreSQL

Install the server, initialize a cluster, start the service, and create a role.

Choose the installation route appropriate for your operating system. On Windows, use the official PostgreSQL installer and note the password for the postgres administrative role. On macOS, use the official packages or a package manager. On Debian/Ubuntu, use the packaged server. Server version and service names vary; verify rather than assume.

BASH
sudo apt update
sudo apt install postgresql postgresql-client
sudo systemctl enable --now postgresql
sudo -u postgres psql -c "SELECT version();"
BASH
sudo -u postgres createuser --pwprompt analyst
sudo -u postgres createdb --owner=analyst shoplab
psql -h localhost -U analyst -d shoplab -c "SELECT current_database(), current_user;"

The default Linux local peer-authentication path is different from TCP password authentication. The explicit -h localhost uses a TCP connection; if it fails, inspect pg_hba.conf, the service status, and the port before changing security settings. For Windows, create the role and database in psql or pgAdmin using the same SQL below.

SQL
CREATE ROLE analyst LOGIN PASSWORD 'replace-with-a-strong-password';
CREATE DATABASE shoplab OWNER analyst;
CHAPTER 03

Connect VS Code to PostgreSQL

Use a SQL extension and verify the connection without embedding secrets.

Install VS Code, then choose a reputable PostgreSQL-capable SQL extension (for example, Microsoft’s PostgreSQL extension if available in your Marketplace). Open its connection command and enter host localhost, port 5432, database shoplab, username analyst, and your password. Extension menus vary by version. Alternatively, use VS Code’s integrated terminal and psql; this route is reliable even without an extension.

BASH
psql -h localhost -p 5432 -U analyst -d shoplab
-- Once connected, run:
SELECT current_database(), current_user, inet_server_port();

Troubleshooting: “connection refused” usually means wrong host/port or server not listening; “password authentication failed” points to credentials or authentication rules; “database does not exist” means the server was reached but the requested database was not found. Avoid putting passwords in SQL files or source control.

CHAPTER 04

Create the sample database

Create tables, keys, constraints, and indexes for a small store.

A relational design separates entities from events. One customer has many orders; one order has many line items; each line item refers to one product. Primary keys uniquely identify rows; foreign keys prevent dangling references. Monetary values use numeric rather than floating point.

SQL
DROP TABLE IF EXISTS order_items, orders, products, customers CASCADE;
CREATE TABLE customers (
  customer_id integer PRIMARY KEY,
  name text NOT NULL,
  region text NOT NULL,
  joined_on date NOT NULL
);
CREATE TABLE products (
  product_id integer PRIMARY KEY,
  name text NOT NULL,
  category text NOT NULL,
  price numeric(10,2) NOT NULL CHECK (price >= 0)
);
CREATE TABLE orders (
  order_id integer PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers(customer_id),
  ordered_on date NOT NULL,
  status text NOT NULL CHECK (status IN ('paid','pending','cancelled'))
);
CREATE TABLE order_items (
  order_id integer NOT NULL REFERENCES orders(order_id),
  product_id integer NOT NULL REFERENCES products(product_id),
  quantity integer NOT NULL CHECK (quantity > 0),
  unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);

Store the sale-time unit_price on order_items. Otherwise, a later product price change would rewrite the meaning of historical revenue.

CHAPTER 06

Query fundamentals

Filter, sort, limit, handle NULL, and reason about execution order.

SQL is declarative: you describe the result, and the planner chooses an execution strategy. A useful mental model for a SELECT query is FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT (with window and other features adding nuance). This is a logical interpretation, not a promise of physical execution order.

SQL
SELECT order_id, ordered_on, status
FROM orders
WHERE ordered_on >= DATE '2026-03-08'
  AND status = 'paid'
ORDER BY ordered_on DESC
LIMIT 10;

NULL is unknown rather than equal to anything: use IS NULL, not = NULL. Use explicit ORDER BY when result order matters; tables have no guaranteed default row order.

CHAPTER 07

GROUP BY, HAVING, and aggregates

Compute revenue and customer summaries without double-counting.

GROUP BY partitions the input rows into groups. Aggregate functions summarize each group. The important choice is the unit of analysis: line items, orders, or customers. Revenue should be computed from paid line items, not from the products’ current list prices.

SQL
SELECT c.region,
       COUNT(DISTINCT o.order_id) AS paid_orders,
       COALESCE(SUM(oi.quantity * oi.unit_price),0) AS revenue
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.status = 'paid'
GROUP BY c.region
HAVING SUM(oi.quantity * oi.unit_price) >= 10
ORDER BY revenue DESC;

Expected result: South has 2 paid orders and $46. North has $8 and fails the HAVING threshold. West has no paid orders and is absent because these are inner joins.

Do not use COUNT(*) to count orders after joining order_items: it counts line-item rows. Use COUNT(DISTINCT o.order_id), or aggregate orders first in a common table expression.

CHAPTER 08

INNER and LEFT JOIN

Understand row multiplication, unmatched rows, and cardinality.

An INNER JOIN keeps matching rows. A LEFT JOIN keeps every row on the left, filling unmatched right-side columns with NULL. A join is not inherently one-to-one: joining an order to its items multiplies order rows according to the number of items.

SQL
-- Every customer, including Dee with no orders:
SELECT c.name, COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;
-- Expected: Ada 2, Ben 2, Cleo 1, Dee 0.
SQL
-- Count paid orders without accidentally dropping zero-order customers:
SELECT c.name,
       COUNT(o.order_id) FILTER (WHERE o.status = 'paid') AS paid_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

Common trap: placing o.status = 'paid' in WHERE after a LEFT JOIN removes unmatched customers. Move the condition into the ON clause or use conditional aggregation, depending on the question.

CHAPTER 09

Business analysis with SQL

Build cohorts, top products, and a repeat-purchase report.

Analytics begins by defining a metric. For paid revenue, use paid orders only and multiply each line item’s quantity by its captured sale price. For customer behavior, aggregate at the customer grain before ranking.

SQL
WITH customer_revenue AS (
 SELECT c.customer_id, c.name,
        COALESCE(SUM(oi.quantity * oi.unit_price)
          FILTER (WHERE o.status = 'paid'),0) AS paid_revenue
 FROM customers c
 LEFT JOIN orders o ON o.customer_id = c.customer_id
 LEFT JOIN order_items oi ON oi.order_id = o.order_id
 GROUP BY c.customer_id, c.name
)
SELECT name, paid_revenue,
       DENSE_RANK() OVER (ORDER BY paid_revenue DESC) AS revenue_rank
FROM customer_revenue
ORDER BY paid_revenue DESC, name;
SQL
SELECT p.category,
       SUM(oi.quantity) AS units_sold,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM products p
JOIN order_items oi ON oi.product_id = p.product_id
JOIN orders o ON o.order_id = oi.order_id AND o.status = 'paid'
GROUP BY p.category
ORDER BY revenue DESC;

For a true cohort analysis, first define a customer’s first paid order date and group by that month. Be careful with sparse data: a cohort with one customer cannot support reliable retention conclusions.

CHAPTER 10

EXPLAIN ANALYZE and indexing

Read plans, distinguish estimates from actuals, and tune responsibly.

PostgreSQL uses statistics and cost estimates to choose among scans, joins, sorts, and aggregation strategies. EXPLAIN shows the planned operations; EXPLAIN (ANALYZE, BUFFERS) executes the query and reports actual rows/timing and buffer activity. Use ANALYZE only when executing the statement is safe.

SQL
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders
WHERE customer_id = 1
ORDER BY ordered_on DESC;

CREATE INDEX idx_orders_customer_date
ON orders (customer_id, ordered_on DESC);
ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 1
ORDER BY ordered_on DESC;

On a five-row table, a sequential scan can be faster than an index scan. That is not a failure. Indexes become valuable when they avoid reading many irrelevant rows, but they also consume storage and slow writes. Do not claim a speedup until you compare measured plans on appropriately sized data.

Performance lab rule: The five-row sample is too small for meaningful timing. Generate at least 100,000 orders in a disposable database, run ANALYZE, collect both plans with EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON), repeat runs, and record PostgreSQL version, row count, cache state, and hardware. Never label a conceptual plan as a measured result.
CHAPTER 11

Performance investigation lab

Compare plans, update statistics, inspect selective filters, and test alternatives.

Performance diagnosis is a hypothesis-driven loop: identify the slow query, collect its plan, compare estimated and actual row counts, check filtering and join cardinality, consider an index or rewrite, then measure again under comparable conditions.

SQL
-- Run before and after each change; save both plans.
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.customer_id, COUNT(*)
FROM orders o
WHERE o.status = 'paid'
  AND o.ordered_on >= DATE '2026-03-01'
GROUP BY o.customer_id;

CREATE INDEX idx_orders_paid_date_customer
ON orders (ordered_on, customer_id)
WHERE status = 'paid';
ANALYZE orders;

Watch for estimated versus actual row count mismatches, unexpectedly large intermediate joins, sorts spilling to disk, and repeated nested-loop work. In real systems, use pg_stat_statements when available to find high-total-time queries; it may require administrator setup.

CHAPTER 12

Safety, maintenance, and next steps

Use transactions, parameterization, least privilege, and backups.

Development convenience is not a production security model. Create separate application roles with minimum permissions; do not connect an app as postgres. Use environment variables or a secrets manager for credentials, TLS where required, and parameterized queries to avoid injection.

SQL
BEGIN;
UPDATE products SET price = price + 1 WHERE product_id = 10;
SELECT product_id, price FROM products WHERE product_id = 10;
ROLLBACK; -- Safe experiment: no permanent change

-- Example backup from your shell:
-- pg_dump -h localhost -U analyst -d shoplab -Fc -f shoplab.dump

A backup is not verified until you can restore it in a separate environment. For deeper learning, practice concurrent transactions, isolation levels, foreign-key indexing, vacuum/analyze, and query-plan comparisons on a larger synthetic dataset.
